## 二、崩溃现场（实验 1，dump 20260920-115714）

```
Access violation - code c0000005
SRTTR 模块基址 = 0x7ff731030000
崩溃 RVA     = 0x105500
指令         = movzx edx, word ptr [rax]     ; rax = 0 → 空指针解引用
```

调用栈（RVA）：`0x105500 ← 0x10366b ← 0x1016b2 ← 0x1687f4 ← 0x198f98 ← 0x311302 ← 0x199273 ← 0xd0cec2 ← kernel32!BaseThreadInitThunk`

**栈上没有任何 SR3R_I18N 帧**（SR3R_I18N 基址 0x7ffaeff50000）。崩溃在**独立线程**。

崩溃点上下文（运行时反汇编）是一个**链表遍历**：
```
0x1054d9  mov  r10, [rbx+0x20]     ; 取链表头
0x1054e0  test r10, r10
0x1054e3  je   0x10552b
0x1054e5  mov  r11, [r14+rsi+0x20]
0x105500  movzx edx, [rax]         ; rax=0 崩溃（rax 应来自 r11/链表节点）
```

## 三、probe 实测（实验 1 运行中）

用原生 probe.exe 跨进程读挂载表（**必须用运行时基址 + RVA**）：

```
runtime_base = 0x7FF731030000    (静态 0x140000000，ASLR 高熵重定位)
count @+0x2967C18 = 3
array @+0x2967C1C = [0]{type=0,param=0,ena=1} [1]{type=1,param=0,ena=1} [2]{type=1,param=6,ena=1}
```

→ **磁盘项确实已在 [0]，vpp 在 [1][2]。改表功能本身成功了。**

## 四、关键事实

1. **挂载表数组基址 = `+0x2967C20`（静态 `0x142967C20`）**，每项 12B：
   `+0 type / +4 param / +8 enabled(u8)`。count 在 `+0x2967C18`（与数组相邻，无 padding）。
   - ⚠️ 本次 probe 对 count 与 array 的两次 64B 读取在 `C20/C24` 处**不一致**
     （count 读 C24=1；array 读 C24=0）——当时游戏**正在注册中**，内存变动。
     **数组基址以 IDA 反编译为准（C20）**，代码里 `lea 出 C24 再 -4` 的补偿是**正确**的。
2. 注册器 `sub_14084D5A0` 与遍历器 `sub_14084DEE0` **共用同一把临界区**
   `stru_142967DA8` → 表操作互斥安全，**排除并发撕裂**。
3. 注册器只有 **3 个调用点**，全部在 `sub_1401673B0`（WinMain 内），连续三行：
   ```
   0x140167678  MountReg(0, 0, 0)   ; 磁盘项 → [0]
   0x140167686  MountReg(1, 6, 0)   ; → [1]
   0x140167693  MountReg(1, 0, 1)   ; insertFront → 顶到 [0]，把磁盘项挤到 [1]
   ```
4. **遍历器的过滤条件**：`if (!enabled || (a4 != -1 && a4 != param)) skip;`
   —— `a4` = 调用方传入的 pool id；磁盘项 param 恒为 0。
5. 崩溃点 `RVA 0x105500` 在 **IDA 库的"空洞"区**（`0x14104000~0x14107000` 无函数）。
   原因：`SRTTR.exe` 磁盘文件**加壳**（TimeDateStamp 0x60EE85F4 / EP 0x02993000 /
   SizeOfImage 0x40000000 明显非法），IDA 库对加壳态建立，运行时是解壳后布局。
   → **IDA 的代码覆盖 ≠ 运行时布局**，但**数据区（0x140000000+0x29xxxxx）一致**，
   故挂载表/字体表等全局地址可信。

## 五、根因（v7.8.2 修法不完整 → v7.10 根治）

### 5.1 v7.8.2/v7.8.3 的判断（不完整）

初判为「**改表时机竞争 —— 在引擎注册序列执行中途插队**」，修法是等 `count>=3`
且连续 4 次采样（200ms）不变才动手。

该修法**没有解决问题**：2026-10-11 的客户机 dump 仍是同一处崩溃
（`SRTTR+0x8D0BE0`，`mov rax,[rcx+0x18]`，rcx=0），而客户机日志显示
`ApplyLooseFirst -> count 3->3, disk item idx 1 -> 0` 已成功 —— 说明崩溃发生时
**插队动作本身是"合法"的，问题不在时机早晚**。

### 5.2 真正的根因：改表撞上「游标式」读者（v7.10 结论）

挂载表有两类读者：

| 读者 | 加锁方式 | 是否危险 |
|---|---|---|
| `sub_14084DEE0`（统一打开器主遍历） | 整调用持锁 | 安全 |
| `sub_14084DD60` / `sub_14084E140` | 整调用持锁，但**下标游标存在调用方** | **危险** |

后两者是**游标式**的：起始下标由调用方保存（`*a1`），函数内部
`v9 = *a1 + 1; *a1 = v9;` 写回，调用方循环调用直到返回 0：

```c
// sub_14084DD60(unsigned int *a1, ...)   a1[0] = 跨调用保持的游标
EnterCriticalSection(&stru_142967DA8);
v9 = *a1;                       // 从调用方上次的位置继续
while (...) { ... v9 = *a1 + 1; *a1 = v9; ... }
LeaveCriticalSection(&stru_142967DA8);
```

**临界区保护不了这个**：游标是调用方的状态，不在锁的覆盖范围内。

而 `MountReg(insertFront=1)` 是一次**整表 memmove**（`[0..v6-1]` 整体后移一格）。
若此刻有游标循环正在进行，下标语义立刻改变 → **条目被跳过或重复访问** →
下游资源槽为 NULL。

它与崩溃现场吻合：
- 崩在 `SRTTR+0x8D0BE0`：`mov rax,[rcx+0x18]`，`rcx = slotTable[index] = 0`
- 调用者 `sub_14031EBE0`（返回地址 `0x31ED7A`）**不检查 NULL** 就调用了那个
  非防御式校验器
- 栈上是任务/活动装载路径（`sub_14042D750` / `sub_14042C750`，栈字符串
  `dlc1_sr3_city_missions.asm_pc`）—— 正是装载期
- 该路径与文本无关，是**资源装载器**的槽位校验

游标式读者的调用方都在装载期：`sub_14042D750`（关卡/`.asm` 装配）、
`sub_14042C750`、`sub_1408C0C90`（着色器库，`.fxo_pc_dx11`，启动期即跑）。

### 5.4 v7.10 修法：静止点插队

注册器在整个映像里只有 3 个调用点，全在 `sub_1401673B0` 内连续执行：

```
0x140167678  MountReg(0, 0, 0)   磁盘项 → [0]
0x140167686  MountReg(1, 6, 0)             → [1]
0x140167693  MountReg(1, 0, 1)   vpp 插队  → [0]，把磁盘项挤到 [1]
```

第 3 次返回后 `count==3`，而引擎此时**尚未开始装载资源**（本地化初始化
`sub_1403FDA90 → sub_1403FD430` 还在后面）。**这是本进程唯一的静止点**。

改法：hook 注册器，在其每次返回后复核「磁盘项是否在 [0]」，不在就补一次
`MountReg(0,0,1)`。最终布局 `[0]={0,0} [1]={1,0} [2]={1,6}` 与旧版一致
（语义零变化），但**不再有运行期异步窗口**。

- 主路径：`HookMountReg`（SR3R v7.10 / SR4R v2.1）
- 兜底：装晚了 / 装失败 → 回退旧的 `LooseFirstWatcherThread`（保留 v7.8.3 的
  保守判定），日志出现 `loosePath=watcher-fallback`
- 自检：每次插队后打印 `mountlayout[after-hoist]`，布局偏离预期立刻可见

### 5.5 验证要点

1. 日志应出现 `mountreg[hook]: 已 hook 注册器` →
   `静止点插队 calls=3 ... diskIdx 1 -> 0 OK` → `mountlayout[after-hoist]`
2. **必须走进世界**（读档/新开游戏进城）—— dump 的栈就在活动/任务装载路径上，
   只到主菜单不算过关
3. 正常路径下**不应再出现** `mountreg: 注册序列进行中` / `mountreg[watch]` 行

### 5.6 仍未闭环的部分

崩溃机 dump 是 `MiniDumpNormal`（2.7MB，**未捕获堆**），无法直接读出那个 NULL
槽的真实归属。要彻底钉死需一份 `MiniDumpWithFullMemory` 或 PageHeap 复现。
本修法不依赖该链条的最后一环 —— 把异步窗口消掉，危险即不存在。

## 六、附：关于 `update\` 目录

`update\` **不是游戏原生机制**，而是 Ultimate ASI Loader 的
「Override (Update) Folder」虚拟覆盖目录（`winmm.dll` 导出
`AddVirtualFileForOverloadA/W`、`AddVirtualPathForOverloadA/W`；
UTF-16 串 `Select Override (Update) Folder`、`update\global.ini`）。

证据：fsprobe 日志中引擎请求的是**裸文件名**（`[hit ] static_us.le_strings`，
无 `update\` 前缀），而文件实际只存在于 `update\` 下 —— 说明是 Loader 的 API 层
重定向，不是引擎拼的路径。

含义：`update\` 的行为受 Loader 版本 / `global.ini` / 用户往该目录丢的任何文件
影响，属于**我们不可控的外部依赖**。
