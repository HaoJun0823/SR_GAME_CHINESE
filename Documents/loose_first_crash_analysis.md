## 二、崩溃现场（实验 1，dump 20260920-115714）

```
Access violation - code c0000005
SRTTR 模块基址 = 0x7ff731030000
崩溃 RVA     = 0x105500
指令         = movzx edx, word ptr [rax]     ; rax = 0 → 空指针解引用
```

调用栈（RVA）：`0x105500 ← 0x10366b ← 0x1016b2 ← 0x1687f4 ← 0x198f98 ← 0x311302 ← 0x199273 ← 0xd0cec2 ← kernel32!BaseThreadInitThunk`

**栈上没有任何 SR3R_I18N 帧**（SR3R_I18N 基址 0x7ffaeff50000）。崩溃在**独立线程**。

崩溃点上下文（运行时反汇编）是一个**链表遍历**：
```
0x1054d9  mov  r10, [rbx+0x20]     ; 取链表头
0x1054e0  test r10, r10
0x1054e3  je   0x10552b
0x1054e5  mov  r11, [r14+rsi+0x20]
0x105500  movzx edx, [rax]         ; rax=0 崩溃（rax 应来自 r11/链表节点）
```

## 三、probe 实测（实验 1 运行中）

用原生 probe.exe 跨进程读挂载表（**必须用运行时基址 + RVA**）：

```
runtime_base = 0x7FF731030000    (静态 0x140000000，ASLR 高熵重定位)
count @+0x2967C18 = 3
array @+0x2967C1C = [0]{type=0,param=0,ena=1} [1]{type=1,param=0,ena=1} [2]{type=1,param=6,ena=1}
```

→ **磁盘项确实已在 [0]，vpp 在 [1][2]。改表功能本身成功了。**

## 四、关键事实

1. **挂载表数组基址 = `+0x2967C20`（静态 `0x142967C20`）**，每项 12B：
   `+0 type / +4 param / +8 enabled(u8)`。count 在 `+0x2967C18`（与数组相邻，无 padding）。
   - ⚠️ 本次 probe 对 count 与 array 的两次 64B 读取在 `C20/C24` 处**不一致**
     （count 读 C24=1；array 读 C24=0）——当时游戏**正在注册中**，内存变动。
     **数组基址以 IDA 反编译为准（C20）**，代码里 `lea 出 C24 再 -4` 的补偿是**正确**的。
2. 注册器 `sub_14084D5A0` 与遍历器 `sub_14084DEE0` **共用同一把临界区**
   `stru_142967DA8` → 表操作互斥安全，**排除并发撕裂**。
3. 注册器只有 **3 个调用点**，全部在 `sub_1401673B0`（WinMain 内），连续三行：
   ```
   0x140167678  MountReg(0, 0, 0)   ; 磁盘项 → [0]
   0x140167686  MountReg(1, 6, 0)   ; → [1]
   0x140167693  MountReg(1, 0, 1)   ; insertFront → 顶到 [0]，把磁盘项挤到 [1]
   ```
4. **遍历器的过滤条件**：`if (!enabled || (a4 != -1 && a4 != param)) skip;`
   —— `a4` = 调用方传入的 pool id；磁盘项 param 恒为 0。
5. 崩溃点 `RVA 0x105500` 在 **IDA 库的"空洞"区**（`0x14104000~0x14107000` 无函数）。
   原因：`SRTTR.exe` 磁盘文件**加壳**（TimeDateStamp 0x60EE85F4 / EP 0x02993000 /
   SizeOfImage 0x40000000 明显非法），IDA 库对加壳态建立，运行时是解壳后布局。
   → **IDA 的代码覆盖 ≠ 运行时布局**，但**数据区（0x140000000+0x29xxxxx）一致**，
   故挂载表/字体表等全局地址可信。

## 五、根因（v7.8.2 / v1.9.2 已修）

**改表时机竞争 —— 在引擎注册序列执行中途插队。**

引擎在 `sub_1401673B0` 里**连续**调 3 次注册器，`count` 依次 1→2→3。
v7.8.1 的守候线程只要看到 `count != 0` 就立刻插队：

```
游戏:  MountReg(0,0,0)  → count=1
DLL :                       ← 守候线程抢到锁, 插队! count 仍=1, 表被改动
游戏:  MountReg(1,6,0)  → 写 [1]
游戏:  MountReg(1,0,1)  → 插队到 [0]
```

虽然最终 `count==3` 且布局"看起来正确"，但引擎在其注册调用返回后立刻用返回值/中间
状态做了后续初始化推导（注册器返回 `char`，且表状态被引擎作为后续判断依据）→
后续线程在链表遍历时空指针崩溃（`movzx edx,[rax]`, rax=0）。

**修法（v7.8.2 / v1.9.2）**：`ApplyLooseFirst` 增加「注册序列已结束」判定 ——
必须 `count >= 3` 且**连续 4 次采样（×50ms）不变**才动手；守候线程也不再
「表非空就退出」，一律以 `ApplyLooseFirst` 返回 `true`（已插队成功）为准。
