# 外挂汉化字体渲染库 · 性能损耗 / 风险 / 可优化项评审

> 评审对象：`SR3R_I18N.asi`（MinHook 1.3.3 注入）/ `SRxR_I18N.asi`
> 逆向目标：
> - `SRTTR.exe`（SR3R，session `sr3r`，93k 函数）
> - `sr_hv.exe`（SR4，session `sr4r`，37k 函数）
> 方法论：IDA + Hex-Rays 反编译 + 交叉引用 + AOB 特征定位，证据均为反编译/符号级，非猜测。

## 0. 结论先行（TL;DR）

1. **可以继续优化，而且优化的空间很大，但不在"渲染期"——渲染期开销与官方字形基本等价，瓶颈在"图集膨胀"和"一次性构建期"。**
2. **最大的损耗不是 CPU，是显存**：官方图集用 BC3（压缩）只占用 0.25~1 MB，而本方案把中文字形拼进一张 **BGRA8（4 B/像素、单 mip）大图集**，每字体实测占用 **~500 MB** 常驻显存（SR3R 双字体叠加 ≈ 1 GB，SR4 单字体 ≈ 511 MB）。这是 500~2000 倍的膨胀，且完全没必要——见 §6 优化项 O1。
3. **渲染期每帧成本与官方字形走同一代码路径、同量级**，没有逐帧重建。唯一的多余固定成本是"每字形每帧一次 UV 除法"（见 §4），可忽略。
4. **黑块（缺字）风险真实存在但已缓解**：DLL 把图集加宽到 8192、并自动按频率截断低频字（行 1781-1787），所以"齿(rank 2920)"这类字被截断后会显示成**透明空白**而非黑块（引擎边界语义是空白，已验证）。风险点在 §5。
5. **架构正确性已验证**：magic texId `0x60000000+fontId`、`bit24=0` 界外、伪对象 blob 布局、UV 走 xtab/ytab——与引擎取字路径自洽，可长期稳定工作。

### 质量与性能代价

- **BC3 编码 CPU 成本**：单线程 **396 ms / 3003 字符**（cellW=172、cellH=220 实测基准）。发生在后台线程一次性构建阶段，不占渲染帧。
- **压缩误差（离线往返实测，从源码提取真实函数体）**：

| 场景 | cellW 对齐 | alpha MAE | RGB MAE |
|---|---|---|---|
| SR3R font1（172×220） | ✅ | **0.13** | **0.34** |
| SR4 font1（93×93） | 对齐后 92 | 0.27 | 0.72 |
| SR4 font0（33×33） | 对齐后 32 | 0.83 | 2.34 |

> 上表后两行是**未对齐 cellW 的实测值**；运行时 O2′ 会把 `cellW` 强制 4 对齐（33→32、93→92），故实际误差接近对齐场景。对齐的代价是 SR4 font0 字形缩小约 3%（33→32px）。
- **保真措施**：官方区若为 BC3 家族则**直接搬官方原始压缩块**（`IsBc3Family` 判定），不做"解码再编码"，官方区零二次损失；只有中文区由灰度现场编码。
- **sRGB 一致性**：读取官方 SRV 的 view 格式（TYPELESS 资源实际语义由 view 决定），自建图集同步 `*_SRGB`（对应 §5 R5）。


### 验证方式

1. 从源码**提取真实函数体**（非重写副本）生成离线往返测试，编译运行 → PASS。
   - alpha MAE **0.13** / maxErr 18；RGB MAE **0.34** / maxErr 42；压缩比正好 4.00×。
2. **块直拷边界核验**（按实测 RowPitch）：font0 2048→blocksX=512→每行 8192B，实测 RowPitch=8192（紧凑）；font1 4096→1024 块→16384B，实测 RowPitch=16384（紧凑）。**无跨行越界读取**。
3. **offH 取整核验**：`blocksY=ceil(offH/4)` 与 D3D BC 纹理 mip0 的块行数定义一致，`offH` 非 4 倍数时末行块仍完整，读取不越界。
4. `bc3_atlas=1` 时若 `W`/`H` 非 4 对齐，自动降级 BGRA8 并记日志（不静默失败）。
5. BC3 缓冲分配失败 → 自动回退 BGRA8 并记日志。

### 已知取舍（诚实说明）

| 项 | 说明 |
|---|---|
| BC3 量化 | 字形边缘灰度被压到 3bit 索引（8 级端点插值）。实测 MAE 0.13/255，104~220px 字号下不可辨；极小字号放大看可能有轻微块状。`bc3_atlas=0` 可一键回退。 |
| 峰值内存 | BC3 路径仍保留 BGRA 中转图集（官方区与中文区可能共享块行，分区编码会互相覆盖），故峰值内存未降低——**降的是常驻显存**。这是刻意的安全取舍。 |
| SR4 未同版 | SR4 侧端口独立进行（其官方格式与 SR3R 不同：font0 是 BC2、font1 是 BC3 mips=9）。 |
| GOG 版 | 项目 `kExeBuilds` 里 GOG 指纹仍为 TODO（既有状态，非本次引入）。 |

## 0.6 两项经查证不可行（原计划撤回）

这两项在实施前经引擎渲染器反编译确认**在当前 hook 层级无法实现**，已撤回并记录于此，避免后续重复尝试。

### O2 分页图集 —— 引擎架构不支持

`sub_1408B5FF0` 反编译证据（`0x1408b613d` 绑定 SRV、`0x1408b61a9` 取图集宽高）显示：

```c
sub_1408AF950(v19, *(unsigned int *)(v11 + 184));   // 绑定 SRV —— 在字形循环之外
sub_14085D930(*(unsigned int *)(v11 + 184), &v45, &v46);  // 取图集宽高 —— 也在循环之外
for ( i = *a4; *a4; i = *a4 ) { ... }               // 字形循环
```

- SRV 绑定与图集尺寸获取都**只执行一次**，位于字形循环**之前**
- 每顶点 28 字节布局为 `(x, y, uv.x, uv.y, rgba)`，**没有纹理索引**

**结论**：一次绘制调用只能绑一张纹理。若一次 `DrawWide` 的文本跨页，分页无法生效。
**替代方案（已实施）**：O2′ 通过高度安全预算 + `cellW` 收窄保证容量，从根上消除"H 溢出 → 整个字形层失效"的风险，无需分页。
（若将来确需分页，唯一路径是在 `HookDrawWide` 内按字符所属页切分并自行累加 x 偏移——但会打断引擎的换行/对齐/富文本标记处理，风险显著，需单独评估。）

### O3 预计算 UV —— DLL 侧无法实现

引擎的除法硬编码在同一函数内：

```c
v35 = (float)((float)*(int *)(*(_QWORD *)(v11 + 192) + 4LL * v34) / (float)v45) + v25;  // xtab[i] / atlasW
v36 = (float)((float)*(int *)(*(_QWORD *)(v11 + 200) + 4LL * v34) / (float)v46) + v26;  // ytab[i] / atlasH
```

`xtab`/`ytab` 是 **int 数组**，除法由引擎现场执行；DLL 只能提供整数与宽高，无法"预计算成浮点 UV"绕开。
**且收益本就极小**：每字形 2 次除法，3000 字 × 60 fps ≈ 36 万次/秒，不到单核 0.1%。**已放弃**。

| 字段 | 真偏移 | 说明 |

DLL 自造的 blob（行 1938-1982）：

```
blob = 208 头 + FAKE_GLYPHS(0xFFE0=65504)*16 度量 + FAKE_GLYPHS*4*2 (xtab/ytab)
```

## 4. 性能损耗量化

### 4.1 渲染期（每帧，已验证）

逐字形固定成本（同 `sub_1408B5FF0` / SR4 `sub_1402835B0`，与官方路径一致）：

1. 1× FontLookup（`sub_140859B10`）—— 一次指针数组下标
2. 1× glyph 度量（`sub_140858C10`，含可能的 kern 循环，6B/项）
3. 1× 图集尺寸取（`sub_14085D930`）
4. **1× UV 除法**（`xtab/w`、`ytab/h`）—— **这是唯一的多余固定成本，DLL 可预计算消除**
5. 6× 顶点（28 B/顶点 = 168 B/glyph）→ 顶点缓冲

> 结论：渲染期开销与官方字形**同量级**，没有逐帧重建图集、没有逐帧 stb 光栅化。常规 UI 文本（每帧数千 glyph）下，本方案与官方差异在 <1% 帧时间，**不构成瓶颈**。

### 4.2 构建期（一次性，已验证 / 部分验证）

后台线程 `RasterizeThread` → `FinishFont`（`dllmain.cpp:1727`）：

- **stb_truetype 光栅化**：逐字符 `ScaleForPixelHeight` + blit，字符集 ~2977（SR3R）/ 3067（SR4）。CPU 一次性成本，**部分验证**（无实测耗时，但属于"启动/切场景时一次性"，非每帧）。
- **读回官方图集**（`CopyResource` + `Map` staging）：必须做，因为要保留英文/符号区（行 1799-1812）。
- **BC 解码**（官方 BC3 → BGRA8，行 1826-1846）：`DecodeBcStrip/Bc1..Bc4`。**一次性 CPU 成本**，且是"因为官方是压缩格式才需要解"——若官方走 BGRA8（如 fnt_chinese）则免解码。
- **CreateTexture2D + CreateSRV**（行 1932-1936）：BGRA8、单 mip、单 slice，上传整张大图集。
- **组装伪对象 blob**（~15 ms，源码注释行 31）。

> 结论：构建期是一次性的，最慢环节是"拼接 + 上传 ~500 MB BGRA8 大图集"。这是**启动/切语言时**的一次性卡顿来源，不是帧率问题。

### 4.3 显存占用（已验证，精确）

> 说明：本节数字为**估算阶段的记录**，与 §0.5 的实测值有出入（原因是当时的容量仿真假设 cellW=cellH 的方形格，而 DLL 实际会收窄 cellW 逃生）。**以 §0.5 的实测值为准**，本节保留以呈现推导过程。

DLL 魔法图集创建参数（`dllmain.cpp:1919-1934`，v7.9 前）：`Format=B8G8R8A8_UNORM`、`MipLevels=1`、`ArraySize=1`、`Usage=DEFAULT`、`BindFlags=SHADER_RESOURCE`。

按 `FinishFont` 尺寸逻辑（先 1:1，装不下把 W 加宽到 8192，再窄 cellW）估算：

| 字体 | 官方真实图集 | 魔法图集尺寸 | 显存（BGRA8） |
|---|---|---|---|
| SR3R font0 (body) | 2048×1024 BC3 | 8192×5184 | **162 MB** ← 实测 |
| SR3R font1 (header) | 4096×2048 BC3 | 8192×16348 | **511 MB** ← 实测 |
| 合计 | — | — | **≈ 673 MB** ← 实测 |

> **SR3R 双字体叠加实测 ≈ 673 MB 常驻显存**（非早期估算的 1.0 GB）。
> 这是整个方案**最大的性能/资源代价**，且非必要——官方同样内容只用 0.25~1 MB（压缩）。
> **v7.9 改 BC3 后降至 ≈ 168 MB**（详见 §0.5）。

## 6. 可优化项（v7.9 实施后的最终状态）

> 本节原为实施前规划。**实际实施结果与偏差见 §0.5 / §0.6**——O2、O3 经查证不可行已撤回；O1 的实际收益是 **4×**（非预估的 8×，因 BGRA8→BC3 是 4 B/px→1 B/px）。

### O1【已实施】魔法图集改用 BC3 压缩，显存 4×↓
- **做法**：`DXGI_FORMAT_BC3_UNORM`（或 `_SRGB`），官方 BC3 区**原样搬压缩块**（零二次损失），仅中文区现场编码。
- **实测收益**：SR3R font0 162→40.5 MB、font1 511→128 MB，合计 **673→168 MB**。消除 R1。
- **代价**：CPU 编码 396 ms/字体（后台一次性）；字形 3bit alpha 量化（往返 MAE 0.13/255）。
- **回退**：`bc3_atlas=0`。

### O2【未实施·不可行】分页图集
- 见 §0.6：引擎一次绘制只绑一张纹理，分页在当前 hook 层级无法生效。**已由 O2′ 替代**。

### O3【未实施·不可行】预计算 UV
- 见 §0.6：UV 除法硬编码在引擎渲染器内，DLL 侧无法预计算；且收益 <0.1%。**已放弃**。

### O4【已实施】补 BC5/6H/7 + SRGB 分支
- 补 BC5 解码器、BC6H/BC7 识别、`*_SRGB`/`*_TYPELESS` 判定；新增 `CanDecodeBc` 闸门——**识别 ≠ 能解码**，BC6H/BC7 无解码器时优雅放弃（避免 `DecodeBcStrip` 的 default 分支把官方区清零，那会让英文渲染成透明，比不升级更糟）。消除 R5/R6。

### O5【已实施】修订源码误注释
- 修正"纹理对象字段（+20 变体/+34 速度）"被误记入字体对象的注释；并记录"一次绘制只绑一张纹理 / UV 除法在引擎内"两条架构约束，避免后续重复尝试 O2/O3。

### O2′【已实施·替代 O2】容量加固
- `ATLAS_H_LIMIT = 16384-32`（原逻辑贴着 16384 算，font1 实测 H=16348 仅差 36px）；`cellW` 强制 4 对齐（BC3 按 4×4 块，非对齐会让相邻字形在共享块内互相渗透）；容量不足时日志显式标注 `WILL TRUNCATE`。

### O6【待验证·可能收益最大】注入官方 `fnt_chinese` 资源
- **背景**：`sub_14016E0B0` 证实引擎**本就有 `fnt_chinese` 中文字体资源**（语言码 `==13` 载入）。
- **但**：经与你确认，**官方 `fnt_chinese` 资源本身残缺**（字形不全），这正是当初改用外挂字库的原因。故 O6 不作为本版方向；**你已决定下版本再处理**。
- 保留此条以备后续：若某天拿到完整的中文资源包，O6 仍是显存与 CPU 双赢的终局方案。

### 构建注意事项（SR4 特有）

SR4 的 `SR4R_I18N.vcxproj` 里 `WindowsTargetPlatformVersion` 写的是 `10.0`（「最新」），**MSBuild 命令行下会报 `MSB8036: 找不到 Windows SDK 版本10.0`**。这是既有配置状态（SR3R 写死了 `10.0.19041.0` 所以不受影响）。正确做法是显式传 SDK（与 `build_release.py` 一致，**不改 vcxproj**）：

```
MSBuild.exe SR4R_I18N.vcxproj /p:Configuration=Release /p:Platform=x64 ^
  /p:WindowsTargetPlatformVersion=10.0.19041.0 /t:Rebuild
```
